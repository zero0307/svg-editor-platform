## Phase 2 报告的维护要求

每个板块完成后，将设计位置更新为真实的代码文件、函数、测试和证据。最终报告通过本入口包含或链接以下内容：

| 内容         | 完成时应具备                                                                                     |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 四扩展点清单 | 接口、职责、实际调用文件与函数、实现、禁用行为和违反契约的报错                                   |
| 重构前后架构 | PlantUML 源文件、渲染结果与实际依赖规则；当前[目标源图](architecture/phase2-proposed.puml)为方案 |
| 两种装配     | 启动方法、配置格式、路径解析、options、清单校验与失败回滚                                        |
| 设计模式     | Command、Composite、Adapter、Decorator 的实际角色、差异与 OCP 验证                               |
| 架构决策     | 不少于三条 ADR，并覆盖正文明确要求说明的契约与取舍                                               |
| VSCode 实践  | 安装启动、样例 SVG、真实运行截图、异常输入和代码复用分析                                         |
| DSH 插件     | 固定版本、安装卸载、工具接口、能力边界和真实会话演示                                             |
| 过程记录     | 实际讨论、AI 建议检查与纠正，关联 Issue、PR 和提交                                               |
| 质量保证     | 独立测试、兼容回归、A/B 输出 diff、插件接入提交 diff 和真实日志                                  |
| 一致性自查   | 实际目录、接口、依赖与方案的差异、理由和修订记录                                                 |
| 指标与交付   | 从 Git 历史生成的指标、最终提交、`p2`、仓库地址与评阅访问验证                                    |

报告放在 `doc/`，指标按课程要求放在 `docs/metrics/`。每项完成状态以实际实现和验证为准；未执行的检查保持待验证，不能用计划或历史结果替代。
