# 文档与过程记录维护规则

文档随代码和验收一起更新。需求来源、设计决策、实现状态和运行证据分别维护，避免把未完成方案写成结果。

## 唯一维护位置

| 内容               | 位置                                             | 更新时机                                       |
| ------------------ | ------------------------------------------------ | ---------------------------------------------- |
| 原始课程要求       | 根目录两份规格原文                               | 收到新版本时保留旧版和来源，不自行修改要求     |
| 项目启动与导航     | 根 `README.md`                                   | 启动方式、依赖或目录变化                       |
| 课程报告入口       | `doc/README.md`                                  | 每个里程碑；链接实际代码与子文档               |
| 当前架构与依赖规则 | `doc/architecture.md`及`doc/architecture/*.puml` | 接口、模块或依赖方向变化                       |
| 当前开发任务       | GitHub Issues/PR                                 | 认领、受阻、待审、完成；不另手抄一份任务状态表 |
| 需求到验收的映射   | `doc/acceptance.md`                              | 新增测试、证据或规则变更                       |
| 设计决策           | `doc/adr/`                                       | 影响跨块契约、兼容、状态或失败策略时           |
| 关键过程与AI纠正   | `doc/records/`                                   | 有代表性的检查、错误、取舍和修正发生时         |
| 验收证据           | `doc/evidence/<milestone>/`                      | 真实运行后，保存输入、输出、环境及commit       |
| 输入命令会话       | `doc/transcript/`                                | 需求变化；仅命令和注释，不带提示符或期望输出   |
| SVG与固定目录夹具  | `test/fixtures/`                                 | 增加受控输入；dir运行日志放在被测目录外        |
| 审阅后的期望输出   | `test/fixtures/expected/`                        | 经过审阅的行为修正，不能用新实现输出覆盖旧基线 |
| 架构指标           | `docs/metrics/`                                  | 脚本按Git历史生成，不手填数字                  |

报告引用路径时标注最终代码文件与函数；开发中的路径写“拟建”，实现后改成实际位置。不会要求成员为每次小改写一篇记录；只有关键决策和代表性 AI 纠错需要单独记录。

## 最小文档闭环

每个功能 Issue 写清目标、负责目录、所需接口和验收方式。任务定义与真实Issue索引维护在 `doc/tasks/`；认领和完成状态只在GitHub维护，依赖调整同时同步正文与原生blocked by关系。对应 PR 给出实际行为、测试命令及结果；若接口或架构有变化，关联 ADR 和矩阵条目。完成时更新对应板块文档，记录已经生成的证据，Issue 通过 PR 关闭。

ADR 采用 `Proposed → Accepted → Superseded` 状态。方案评审后再标 Accepted；被替代的决策保留原文并链接后继，不能把当时的不同取舍删得没有痕迹。已使用0001初始化、0002 CI协作；后续编号从0003继续，例如 `0003-plugin-boundary.md`。编号只表示记录顺序，不能复用旧编号。

AI 记录至少包含“建议是什么 → 检查了什么 → 发现什么 → 如何修正 → 如何验证”。不保存隐私或无关完整对话，也不能只写“AI生成后测试通过”。未运行测试应如实记录未运行和原因。

## 证据要求

日志中同时记录命令、工作目录、Node/npm/DSH版本、被测提交和结果。CLI逐字节比较分别保存输入、标准输出和标准错误；临时目录的 `dir` 日志放到目录之外。截图必须来自实际运行，附对应样例和操作步骤；截图不能代替事务和回滚测试。

指标脚本记录 `final^{commit}` 和目标提交。生成 `p2` 最终指标时避免循环：在候选提交上生成指标并写明“measured commit”，确认后以只含报告/指标的收尾提交打 `p2`；脚本再核对最终 tag 的 CLI源码与 measured commit 完全相同。若 CLI源码有变，重新测量。脚本必须同时支持直接以已存在的 `p2` tag重跑，产物写临时目录，不修改被测历史。

A/B证据保存框架基线、插件提交、两种方式的模块集合/顺序/options和运行目录。用实际存在路径检查 diff，并包含原始 `git diff --name-status C^ C`。不以搜索无结果或不存在路径产生的空 diff 作为通过证据。

## 每个里程碑的收口

由功能板块填写实际结果，集成协调者检查：文档里的命令是否能执行、接口是否与源码一致、矩阵是否能找到测试、日志是否来自当前代码。未完成项保持未完成，列入 Issue；最终报告不保留误导性的完成勾选。
