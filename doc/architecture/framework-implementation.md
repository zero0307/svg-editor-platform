## #2 要交付什么接口

契约由 core 声明。框架提供端口，宿主连接实际服务，消费方可换上同形状的替身。下表是 #2 的交接清单，正式签名和对应测试在契约 PR 中定稿。各包的依赖方向和详细错误语义见[架构方案](../architecture.md)。

| 接口                                                        | 调用约定                                                                                                                                 | 最小验收样例                                                                                                                  |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `Command`                                                   | 命令声明名称、用法、文档前置条件和本次调用的效果。查询只取只读视图或目录端口，编辑交给事务。已知命令先按原顺序检查文档，再报告参数错误。 | 未 init 时调用参数错误的编辑命令，错误优先级与基线相同。无文档的目录查询可以执行。`canvas` 查询保留历史，调整尺寸才设置屏障。 |
| `ShapeProvider`                                             | 创建服务按领域类型分发。读回按标记和标签选 provider，并传入完整子树。图形可克隆、校验、提供序列化信息。                                  | 测试容器可创建、嵌套、克隆和读回。克隆保留具体类型，修改副本不改变原件。                                                      |
| `AttributeHandler`                                          | `handles` 只读。零命中走旧属性规则，多命中在写入前报错，唯一命中在本次编辑的候选对象上执行。                                             | 注册两个支持同一属性的实例时，两者的写方法均未调用。唯一处理器部分写入后失败时，文档、历史和 dirty 基准都保持原值。           |
| `TreeDecorator`                                             | 接收只读的根行或节点行，返回行尾标签。在文档操作成功后接收事件。注册顺序决定多个标签的顺序，状态由会话中的实例持有。                     | 两个假标签独立启停，根行和子树均可装饰。零标签的换行、空格和顺序与基线一致。                                                  |
| `EditorSessionPort`                                         | 装配侧按调用创建独立会话。支持初始化、读入、取得只读文档快照、结构化编辑及保存。读入提供 warnings，保存提供实际路径，错误由调用方呈现。  | 同一套消费者用例分别注入假会话和真实会话，从快照读取画布与树，无需分析终端回显。两个实例独立读写。                            |
| `SvgElementView`、`ShapeCreationService`、`DirectoryReader` | 分别提供中立节点数据、按已注册类型创建形状、读取指定目录的直接子项与类型。公开类型归 core，XML 与 Node 适配器分别归 svg-xml 和 host。    | VSCode 可看到无 ID 元素。复合图形可用假创建服务建子件。目录命令可用乱序假目录项验证输出。                                     |

建议 #2 随契约交一份小型消费者示例。以“读入一张图”为例，服务返回画布尺寸、按文档顺序的节点和导入警告。CLI 用它生成原来的 warning 与 read 回显，DSH 用同一数据生成工具结果。流程图布局、DSH 参数 schema 和工具名归应用层。编辑器只需认识结构化编辑操作。

## 从 Phase 1 迁移的四个落点

1. **容器与事务。** 现有 `SvgDocument` 直接创建 `Group` 做画布根，`Group.clone()` 也直接构造普通分组。#7 先提取通用容器和内部画布根，再让 #14 把具体 SVG `g` 交给 builtins。沿用 `EditCommand.execute` 的候选副本流程，调用每个节点的不变量，校验通过才更新历史并通知订阅者。只读视图和事件载荷隔离活文档。用带必需子件的测试容器验证移出子件时回滚、删除整棵子树时成功、克隆的父子引用都指向新树。[现有文档模型](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/src/domain/SvgDocument.ts) · [现有编辑事务](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/src/application/commands/EditCommand.ts)
2. **XML 两个入口。** #6 提供保留源码位置和原始 ID 的语法树，供 Outline 定位。#13 在严格导入层预检全局 ID、补缺失 ID 并记录警告，沿父链计算继承属性及变换，使用完整子树恢复领域对象。以“带变换的容器包含叶子”和“两个子树使用相同 ID”分别验成功与失败。专用语义 provider 缺席时允许标记组回落到普通 `g` 并保留元数据。已命中 provider 的结构错误需保留原文档。[现有编解码](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/src/infrastructure/XmlSvgCodec.ts) · [变换与属性继承](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/src/infrastructure/SvgImportContext.ts)
3. **装配与会话隔离。** A 从 CLI 组合根接收模块、清单与 options，B 从配置目录解析启用的模块。二者调用同一个 installer。激活写入暂存区，按类别查重、核对四类贡献名称，校验完成才发布注册和订阅。#8 用故障模块覆盖找不到模块、无默认导出、清单不符、激活异常、重复名和非法配置。另验被禁用的模块从未求值、依赖求值失败有正确归类。#9 提供原子文件写入和目录读取。会话、历史和有状态的标签实例按会话创建。[加载错误与输出格式](../../phase_cli_2-研-1.md)
4. **真正切换 CLI。** #14 把命令注册与六种图形的帮助顺序交给 builtins，保留 REPL、脚本入口、错误后继续和退出码。现有测试装配器、CLI 子进程测试与视觉脚本均引用旧路径。迁移这些入口后在干净检出上构建，分别比较输出、错误、退出码及 SVG。回归还要覆盖读 A、另存 B、再无参数保存仍指向 A，以及保存后编辑再 undo 回到保存点。[命令分发](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/src/cli/CommandRouter.ts) · [测试装配器](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/test/TestHarness.ts) · [视觉检查](https://github.com/zero0307/svg-editor-platform/blob/e5621a68afd4731626d54566f17ba55885d1bc0f/scripts/verify-visual.mjs)

## 何时允许功能插件接入

#15 用一个仅存在于测试夹具的复合图形和少量假贡献贯穿以下场景。此时框架代码已经覆盖正式插件所需的调用路径。

1. 关闭可选扩展，以相同输入和初始文件运行 `final`、框架 A、框架 B。分别比较 stdout、stderr、退出码和落盘结果。同一固定目录的日志写到目录外。
2. 加载测试扩展，经过真实 CLI 创建图形、修改两个子件、undo/redo、保存、重新读入并渲染标签。再以失败处理器执行相同编辑，断言内容、路径、历史、dirty 和事件数量。读取损坏子树和模拟写盘失败也应保留此前的会话。
3. 从实际调用点补全四扩展点清单。记录首版指标的输入 SHA、生成命令和结果。以普通提交冻结 `F`，记录完整 SHA 并保留 `evidence/p2-framework-base` 分支。此后 #17–#20 可分别接入。

课程要求的新插件差异证据单独在 #21 留存。从同一个 `F` 接入相同 box 实现，A 的既有运行文件只改一个顶层组合根，B 只改配置。记录两次接入提交各自相对父提交的文件差异，并核对真实存在的内核、加载器、渲染器和既有插件目录。所有插件合入后，再用相同插件集合、顺序和 options 回放完整 A/B 会话。[差异与回放验收](../acceptance.md)
