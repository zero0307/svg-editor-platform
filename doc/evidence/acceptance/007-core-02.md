## 2. Issue #7 五条验收逐条结论

### 2.1 多部件修改只形成一个 undo 单元，undo/redo 保留插件运行类型，无共享可变子节点 —— **通过**

证据（`packages/core/test/transaction.test.ts`、`attribute-dispatch.test.ts`）：

- `a multi-part handler produces exactly one undo unit and is not re-run`：`MultiPartAttributeHandler` 一次改动 `box1-rect` 与 `box1-label`；一次 `edit` 后两个属性都变，`undo` 一次同时还原，`redo` 后处理器调用次数仍为 1。
- `undo and redo swap validated snapshots without re-running the action`：`CountingAction.calls` 在 undo/redo 后保持 1，证明复用快照而不是重跑动作。
- `edits keep the plugin runtime type and never share mutable children`：`DemoBoxShape` 类型贯穿 edit/undo/redo；编辑后的子节点是新对象，旧文档子节点属性未被修改。
- 会话用多态 `clone()` 生成候选，测试夹具 `DemoBoxShape.newContainer()` 保留实际类型；内部历史栈 `EditHistory` 不导出可变数组。

### 2.2 部分修改抛错、匹配冲突、校验失败保持文档、路径、dirty 基准、屏障及已有 undo/redo —— **通过**

证据（`transaction.test.ts`）：

- `a partial modification followed by an error keeps every state and the redo branch`：处理器式动作先改 `leaf.fill` 再抛错；文档、`doc.svg` 路径（失败后 `save()` 仍以 `doc.svg` 为目标）、屏障状态与事件都不变，已有 redo 仍可用，随后失败的 save 也不影响 undo。
- `an invariant failure discards the candidate and publishes no event`：候选节点 `validateInvariant()` 抛错时无 `editCommitted`，已有历史可用。
- `an attribute conflict keeps the document and an existing redo branch`：两个处理器命中在修改前抛 `AttributeHandlerConflictError`，redo 仍能恢复先前编辑。
- dirty 基准不在 core 保存；它以提交事件为输入。失败路径不发布任何事件，因此标签插件的 dirty 基准不会前进（`packages/core/test/session.test.ts` 的 `a failed step publishes no event…` 与 transaction 事件断言）。

### 2.3 合法默认属性保持旧行为，未知属性报约定错误，handler 失败不再回退默认处理 —— **通过**

证据（`attribute-dispatch.test.ts`）：

- 无命中：`rect#leaf updated: fill="red"`，与 Phase 1 `SetCommand` 文案一致；`stroke`/`stroke-width` 走原有 `setAttribute` 规则。
- `unknown attribute: label` 直接报错且文档不变。
- `a partial handler failure is propagated without default fallback`：处理器先改后抛，异常原样传播，文档不变，未回退默认路径。
- 冲突检测在修改前完成，错误信息按注册顺序列出双方名称。

### 2.4 普通命令统一经过结构策略，整体删除与必要部件单独移出的语义可测 —— **通过**

证据（`structure.test.ts`）：

- 策略落在公开多态钩子：`Shape.canUngroup()`、`ContainerShape.canRemoveChild(child)`、`ContainerShape.canInsertChild(child)`。
- `DeleteAction`/`AddToAction`/`GroupAction`/`UngroupAction` 全部委托 `StructureService`，命令无法绕过策略。
- 整棵复合删除：`delete removes a whole composite subtree when its parent allows it` 删除 `box1`（含两个必要部件）成功。
- 必要部件单独删除/移出：`cannot remove necessary part: box1-rect`、`cannot move necessary part: box1-rect`；`group rejects a necessary part…` 同样被拒。
- `ungroup` 先查复合规则（`cannot ungroup demo-box: box1`），再查 Phase 1 顶层限制（`cannot ungroup top-level container: g1`），并物化继承样式、保持子节点顺序。
- 容器可拒绝插入：`cannot insert rect#blocked into g#g1`。
- 测试发现并修正：三级子类未重写 `newContainer()` 时 clone 会退回父类、策略丢失；`ProtectedBoxShape`/`RejectingGroup` 补齐钩子后通过，该要求已写入 ADR-0004 供 #19 遵守。

### 2.5 查询不清空 redo 或改变屏障，canvas 查询/修改、保存失败符合 P1 —— **通过**

证据（`session.test.ts`、`transaction.test.ts`）：

- `read-only queries do not clear history or unblock the barrier`：`document()`/`hasDocument()`/无尺寸 `canvas` 后 redo 仍可用；save 后屏障仍阻止 undo，查询不解锁。
- `canvas queries keep redo and the barrier; resizing commits a new canvas`：无尺寸只读；带尺寸克隆后替换并设置屏障，事件 `canvasChanged` 在成功后发布；非法尺寸不改变状态。
- `save failures do not set the barrier, clear dirty state or publish events`：写入/编码失败不设置屏障、不发布 `documentSaved`，文档与历史保持可用。
- `read failures keep document, path, barrier, history and events unchanged`：文件错误、解码错误、校验失败都不替换文档、不记住新路径、不改变屏障与历史。
