## 2. Issue #2 验收标准逐条结论

Issue #2 正文四条验收（Issue #2 · TASK-CORE-01，原文清单；`doc/github/` 是本地忽略目录，不建立仓库内链接）：

### 2.1 接口/fake 通过 strict 编译，示例消费者仅使用公开入口 —— **通过（有保留）**

证据：

- `packages/core/tsconfig.json` `extends` 根配置，`strict`/`noUncheckedIndexedAccess`/`noUnusedLocals`/`noImplicitOverride` 全部生效；`npx tsc -p packages/core/tsconfig.json` exit 0 且无输出。
- 唯一公共入口是包根 [index.ts](../../../packages/core/index.ts)（`package.json` 的 `exports` → `dist/index.js`、类型 `dist/index.d.ts`），四扩展点、只读投影、端口、事件和 fake 均从这里导出；包内没有第二组 `exports`。
- fake 与消费示例确实由同一 strict 编译覆盖：`testing/` 下的 `FakeEditorSession`、`FakePluginContext`、`FakeShapeCreationService`、`FakeShapeRestoreService`、`FakeDirectoryReader`、`FaultyAttributeHandler`、`FaultyTreeDecorator` 均在 `dist/` 中生成，并由 [consumer.test.ts](../../../packages/core/test/consumer.test.ts) 调用。
- “仅使用公开入口”有自动检查：`consumer.test.ts` 的 `consumer examples import only the public package entry` 扫描编译后的 `test/support/*.js`，只允许 `../../index.js` 与相对模块，发现其他 specifier 即失败。

保留意见：该检查是**文本级**的 import specifier 扫描，只覆盖测试支撑文件，不是跨包/全仓库模块图约束；真正的“消费者不得穿透 `src`”需要 #5 的边界检查覆盖 `packages/*`。本节点范围内可以接受。

### 2.3 只读路径不获得可变活文档，`handles` 纯查询，handler 冲突和错误契约明确 —— **部分通过**

成立的部分（类型层 + 测试）：

- `ReadonlyDocument`/`ReadonlyShape` 没有任何写能力（`setAttribute`、`insert`、`remove`、`resize` 均不出现）；`QueryContext` 只提供 `hasDocument`/`document()`，没有 session/edit/history；[document.test.ts](../../../packages/core/test/document.test.ts) 的 `the read-only document projection exposes queries only` 用一个只接受 `ReadonlyDocument` 的函数证明编译期能力收窄。
- `EditAction.apply` 与 `AttributeEditContext.document` 拿到的都是候选文档；`attribute.test.ts` 的 `apply modifies only the detached candidate document` 断言原文档未被修改。
- `handles` 纯查询：`handles is a pure query over a read-only shape` 在调用前后对目标子树 `attributes()` 做快照比较。
- 冲突与错误契约：`AttributeHandlerConflictError` 携带 `handlers` 名称列表，测试断言文案 `ambiguous attribute handlers for box1.fill: …` 且**异常抛出前**候选文档字节不变；命中处理器失败按 `attribute handler failed: …` 传播、不回退默认；`FaultyAttributeHandler('broken-query')` 证明 `handles` 抛错也直接传播。

不成立/有意的收窄：

- 只读是**类型级**的。运行时传给查询与装饰器的对象就是活的 `SvgDocument`/`Shape` 实例，没有 `Object.freeze`、代理或只读包装，`as` 断言即可绕过并直接修改；`handles` 的“纯查询”同样只靠类型与约定，运行期没有检测（无法区分纯读与读后副作用，除非另加审计）。
- [ADR-0003](../../adr/0003-core-public-contracts.md) §4 把运行时保护明确交给 #7 事务：失败时保持文档/历史/dirty 不变。在“本节点只发布契约”的定位下这是合理取舍；但若按验收字面要求“只读路径在运行期也拿不到可变文档”，则本节点不满足，故记为部分通过而不是通过。

对 VSCode 板块的影响：无。本板块不 import `@svgframe/core`（[ADR-0009](../../adr/0009-vscode-adapter-boundary.md) 规定 Outline 消费 `packages/svg-xml` 的中立语法层），因此这条类型级边界不阻塞 #3/#11。

## 3. 作为 VSCode 板块消费者对契约的判断（独立阅读，不是转抄 ADR）

我实际阅读了：[index.ts](../../../packages/core/index.ts)、`domain/ReadonlyDocument.ts`、`domain/ReadonlyShape.ts`、`domain/SvgElementView.ts`、`domain/TreeRow.ts`、`ports/EditorSessionPort.ts`、`ports/DirectoryReader.ts`、`extensions/Command.ts`、`extensions/ShapeProvider.ts`、`extensions/TreeDecorator.ts`、`extensions/AttributeHandler.ts`、`extensions/QueryContext.ts`、`events/EditorEvent.ts`，以及 ADR-0003 与 architecture §4/§7。

1. **VSCode 不消费 core 是正确分层。** 文件标记只需要 `Uri`/`FileType`；Outline 需要“标签、可选 `id`、子元素、源码范围”，而 `SvgElementView` 明确是“源码无关”的（没有 offset/行号），architecture §7 也已把源码位置划给 `packages/svg-xml`。若为了 Outline 给 core 加 range，会让 core 承担编辑器语法容错职责，与 ADR-0009 冲突。因此 #11 只依赖 #6 的语法入口，不 import core。
2. **“只读投影是否够用”按用途分开回答。** 对树标签/只读查询（#10、#19）够用：`tag`/`kind`/`id`/`children()`/`attributes()`/`summary()` 覆盖树行渲染与标签判定；对 Outline **不够，而且不应该够**——`summary()` 是展示串，不是标签结构，也没有源码位置，无法支持点击定位。这是分层正确，不是 core 的缺陷。
3. **ADR 是否覆盖我的用例。** 部分覆盖且不冲突：ADR-0003 本身不涉及 VSCode（消费者表也如此），我的边界由 ADR-0009 固定（四文件拆分、UTF-16 偏移到 `Range` 在 adapter、不按文本猜位置）。两篇 ADR 没有相互矛盾的要求。
4. **可减少未来重复的一条建议。** `SvgElementView` 与 #6 的中立语法树都以“元素名/可选 id/子元素”为核心字段；建议 #6 沿用 `tag`、`id`、`children` 命名（但不共享类型），这样 `svg-xml` 同时生产“语义视图”和“语法树”时字段含义一致，VSCode/CLI 的映射代码都更少。
