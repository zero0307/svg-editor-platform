## 3. 逐字节兼容与双装配回放

### 3.1 输入和输出分离

`doc/transcript/` 只存命令与注释，不含提示符、终端启动命令或预期输出。`test/fixtures/svg/` 存输入 SVG；`test/fixtures/expected/` 存审阅过的预期文本与产物；`doc/evidence/` 存实际运行记录。输入覆盖 P1 §6、§6.1A、§6.1B，以及 stats/dir 新增会话。

原任务书里的示例可能包含对齐空格、历史反馈和启动版本的示意文本。兼容测试必须保留 `final` 实际程序输出；若其与课程硬性要求冲突，先建 Issue 并记录裁决，不能为了让 diff 通过而直接改预期结果。

### 3.2 一次回放的固定条件

1. 先构建，再用 Node 直接启动编译产物，避免把 npm 构建日志混入 CLI 输出。
2. 基础兼容组：Phase 2 禁用全部可选插件，与 `final` 使用同一会话、输入文件、运行目录和非交互模式。
3. 双装配组：A/B 使用相同插件集合、顺序、options、初始文档和 cwd。输出作为原始字节比较，不 trim、不排序、不删除 warning/error。stdout、stderr、退出码分别保存和比较。
4. 运行目录使用隔离 fixture；涉及 dir 时输入脚本、输出日志和编译产物均位于被列目录之外。A/B 开始前将目录恢复到同一固定状态，避免 save 产物改变后一轮列表。
5. 记录 Node/npm、平台、Git SHA、启动参数、环境差异、fixture 摘要和退出码。规范文件固定 UTF-8/LF；每个平台在自身环境比较 A/B，不用全局替换换行掩盖差异。
6. REPL 有意报错的会话仍需继续执行后续命令。现有脚本模式出现错误后退出码为 1，应显式断言，不以“非零一定测试失败”处理全部故障用例。

### 3.3 失败状态不变的证明

序列化相等只能证明部分文档状态。事务测试还要检查节点运行类型、子节点顺序、默认保存路径、历史屏障、undo/redo 行为以及 dirty 观察结果。

至少安排两种前置状态：已有 undo 历史；执行 undo 后已有 redo 历史。故障发生后逐项比较文档只读视图，再实际 redo/undo，确认原操作仍可回放且没有多出一个历史单元。测试可用受控状态快照端口，不能为测试给插件开放可变历史栈。

box 的 clone/undo/redo 测试必须检查复合类型与不变量仍在；不能只比较 SVG 文本，因为失去 box 类型的普通 g 可能暂时输出相同 XML。

## 4. 插件和适配器测试的重点

### 4.1 测试分层

| 层级         | 环境                                        | 重点                                                     |
| ------------ | ------------------------------------------- | -------------------------------------------------------- |
| 内核契约     | 假插件、假文档端口                          | 四扩展点、事务、只读执行、冲突、不变量、事件             |
| 单插件       | 仅该插件＋公开核心 API/测试替身             | 不加载其他插件完成注册与业务测试；插件目录可单独运行测试 |
| 真实适配器   | 临时文件系统、真实 XML codec                | IO 与业务组合、读回、排序、原子写入                      |
| 宿主集成     | 临时模块与配置、编译后 CLI                  | ESM 解析、contributes、失败继续、A/B 一致                |
| 用户可见效果 | VSCode Extension Development Host、实际 dsh | UI 注册、原生视图、安装运行与演示证据                    |

box 插件的单测通过公开领域类创建矩形和文字，或用公开测试替身模拟工厂；不能为单测依赖“先激活全部其他插件”。集成测试再验证它与默认六类图形提供者组合。

### 4.2 Loader 故障矩阵

用微型 fixture 插件分别制造：不存在的顶层模块；有模块但无 default；default 结构非法；activate 先注册 shapes/commands/decorators/attributes 再抛错；声明类别或名称不匹配；与既有名称重复；插件内部重复注册；模块顶层求值抛错；内部依赖不存在；配置 JSON 或字段非法。

每例都在失败插件前后放一个可识别的成功插件，验证：先前成功插件保留、当前插件无任何注册残留、后续插件仍加载、CLI 继续响应。清单比较按“类别＋名称集合”，不因注册顺序不同误报；重复名称仍须拒绝，不能由集合去重吞掉。`enabled: false` fixture 的顶层若会抛错也不能被求值。

顶层模块定位与模块加载分开测试：定位不到请求模块才报 `plugin not found`；定位成功后其依赖失败或执行失败，应走插件失败路径。不得只检查错误代码中是否有 `MODULE_NOT_FOUND`。

若框架允许 activate 订阅事件，订阅也必须纳入暂存/释放契约，失败后不产生幽灵监听；测试注入一次事件，检查失败插件没有收到回调。插件任意自行写文件或启动进程不属于注册回滚能够撤销的范围，activate 契约应限制为注册与可释放资源申请。

### 4.3 dir 与真实文件系统

单位测试用目录访问接口替身返回乱序条目及故障，不 monkey-patch `node:fs`。覆盖名称比较规则、隐藏项、空目录、非递归、无参数和两空格格式。真实测试用 `mkdtemp` 创建中文名、空格名、隐藏文件、多个目录，并在 `finally` 清理。

读取失败不只靠 chmod 制造：其行为可能随平台或进程权限变化。至少使用已删除/不存在目录验证真实适配器错误，权限错误由替身稳定覆盖。符号链接和特殊项的显示策略由 ADR 固定，再按平台能力创建 fixture；不追踪链接目标。子进程设置 cwd，避免并行测试共享修改 `process.chdir()`。

## 5. 新插件接入的 Git 证据

框架与通用契约先合并并通过检查，再从同一框架基线建立两个短期演示分支。A/B 分别保留能直接核验的接入提交 `C_A`、`C_B`，可以保留在受保护的 evidence 分支；最终在主线集成时另行记录映射，不把证据依赖于之后会被删除的本地分支或 PR 临时引用。

A 的运行源码变化仅为新增插件及一个顶层组合根文件；B 仅为新增插件和配置，不改已有运行源码。测试、文档、依赖元数据变化逐项列明。采用合并策略时，不要将框架改造和插件接入压成一个提交，否则 `C^..C` 无法证明零内核改动。

验证脚本须先确认内核、宿主、既有插件路径确实存在，再检查 `git diff C^ C`。除检查必需的内核/既有插件空差异，还检查加载器零变化及全部变更文件是否符合 A/B 白名单。排除本次新插件目录；空路径造成的空 diff 不计为有效证据。保存 `git show` 摘要、完整 SHA、命令与结果到证据索引。

## 6. 指标生成口径

目标是同一脚本、同一规则解析两个 Git 提交中的源文件。脚本通过 Git 读取 `final^{commit}` 与验收目标提交，不使用当前工作区的混合状态，不依赖已安装的旧版构建产物，也不改动原标签。

建议在 `scripts/metrics/` 实现 TypeScript AST 分析器，使用仓库锁定的 TypeScript 版本与同一解析配置分析两端。脚本输出输入 SHA、工具/规则版本、排除列表、生成命令、每文件指标和汇总，使圈复杂度数字可复现。无需为简单指标同时引入多套质量平台。

| 指标     | 固定规则                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文件范围 | Git 跟踪的 CLI 运行源码；测试、fixture、依赖、dist、生成文件、文档、VSCode 与 dsh 分别排除或另列                                                                          |
| 行数     | 物理行数；空文件为 0；有末尾换行不额外增一行；空行和注释计入。若另报代码行，必须给单独定义，不能混用                                                                      |
| 圈复杂度 | 以函数/方法/构造器/getter/setter 为单元，起点 1；if、循环、catch、三元条件、非 default case、逻辑与、逻辑或、空值合并运算各加 1；规则版本固定，分别报总量、函数数、最大值 |
| 分类     | CLI 内核／装配处／插件三类；XML 适配器及通用宿主支撑归装配处，并在分类清单解释；VSCode 单列，dsh 单列                                                                     |
| 文件职责 | 维护受版本控制的“路径/模式→分类→职责”清单，脚本从 Git 枚举文件并关联；遗漏或重复分类导致失败，不手填文件数和指标                                                          |
| 对比     | 保存两端原始列表与分类汇总；另列旧路径→新路径的模块迁移表，说明功能搬迁引起的类别变化，避免把目录迁移当作复杂度消除                                                       |

旧版 `src/domain/`、`src/application/` 可作为基线内核分类；`src/cli/`、`src/infrastructure/`、`src/bootstrap/` 为装配/宿主侧，注明 CommandRouter 仍含内置命令分发；旧版插件类为 0。新版按实际最终目录分类，六类图形和内置命令移动到 builtins 后属于插件。两端采用相同的目录职责定义，同时公开迁移表，不倒改旧版分类以美化增量。

发布前先以候选提交生成报告，提交报告后得到最终验收提交，重算并验证运行源码指标未变化，再打 `p2`。报告中的代码分析目标 SHA 与 `p2` SHA 若不同，必须清楚写明仅报告/证据文件造成差异；最终验证日志同时记录 `final` 与 `p2` 解引用后的 SHA。这样可避免报告声称自己包含尚未生成的最终提交哈希。

## 7. 检查入口与完成定义

新仓库以团队锁定的 Node 24.x 为主环境，dsh 环境下限按其当前官方开发指南要求设置为 24.9.0；CLI 可另保留 Node 22 兼容检查。Node 22 的成功不代表 dsh 可运行。实际版本、安装与跨平台结果仍须在初始化阶段记录。

保留既有 `npm run check` 的一键体验。框架阶段再接入以下目标检查，脚本落地前不将名称写成已可运行的命令：格式与严格类型构建、架构边界、既有回归、插件独立测试、宿主故障矩阵、基础兼容/双装配、Git 差异证据、文档链接与指标复现。VSCode 和 dsh 的真实宿主演示单独记录，不能由纯单元测试替代。

每个功能完成须同时具备：对应需求 ID；实现与公开契约；必要的成功和失败测试；更新相关文档/ADR；可定位的验证结果；另一板块的复核记录。每个 PR 只勾选实际完成的检查，未运行写明原因及补验任务。

最终验收时 `doc/README.md` 统一链接实际实现的扩展点清单、前后 PlantUML、ADR、会话、证据、指标和交付步骤。第三部分 dsh 的运行标准须先确认，当前不把插件市场发布列为硬性门槛。
